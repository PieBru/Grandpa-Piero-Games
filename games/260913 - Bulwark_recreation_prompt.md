# Prompt: Recreate "BULWARK" — a single-file HTML5 Canvas tower defense game

Use this as a standalone prompt to (re)generate a game closely matching the original. Copy everything below the line into a fresh conversation.

---

## THE PROMPT

Build a complete, single-file HTML tower defense game called **BULWARK** ("Grid line tower defense"). Output one self-contained `.html` file — inline `<style>` and `<script>`, no build step, no external JS libraries (Google Fonts CDN links for the type family are fine). It must run by double-clicking the file.

### 1. Concept & tone
Dark, moody fantasy-military aesthetic. Enemies ("raiders") march along a fixed dirt path from a west spawn cave to an east gate; the player spends coin to build towers on the surrounding grass to stop them before they reach the gate. Copy: terse, tactical, slightly militaristic ("Sector 7 · Hollow Road", "the gate has fallen", "hostiles").

### 2. Visual design system
- **Fonts:** a bold display font for headings/HUD numbers (e.g. "Bungee") + a clean geometric sans for body text (e.g. "Space Grotesk"), loaded via Google Fonts.
- **Palette:** near-black ink background (`#070b15`), navy panel gradients (`#0d1523`→`#16223a`), soft blue-tinted borders (`rgba(150,185,255,.13)`), off-white cream text (`#eef2ff`), muted blue-gray secondary text. Accent colors are semantic: amber/gold = money, coral/red = lives/danger, sky blue = wave/info, mint green = score/success, violet = a special enemy.
- **Ambient background:** a fixed full-viewport layer behind everything with: a large soft radial gradient, a faint dot grid, a faint vertical rule grid, 2–3 large blurred colored "glow" blobs slowly drifting via CSS keyframes, and a subtle scanline overlay. All ignore pointer events.
- **Panels:** rounded corners (12–16px), thin 1px translucent borders, subtle inner highlight + big soft drop shadow, dark gradient fills — a consistent "glass-metal card" language reused everywhere (topbar, side panels, overlay stat chips, shop cards).
- **Buttons:** a chunky "primary" button with a solid bottom shadow that acts as a 3D press-down effect (translateY + shadow shrink on active), gold gradient fill; a subdued "ghost" button with translucent border; a "danger" button in coral for destructive actions.
- **Motion:** small pop/scale animation whenever a HUD number changes; sweeping skewed "WAVE N" banner animation over the board at wave start; scroll-triggered fade/slide-in reveal for lower page sections via IntersectionObserver.

### 3. Page layout (top to bottom)
1. **Topbar / HUD:** brand mark (small rotating gradient emblem + game title + subtitle) on the left, a vertical divider, then a row of 4 stat blocks — Coin, Lives, Wave, Score — each with a small color-coded label, a big number, and a small sub-caption that updates contextually (e.g. "per kill +9", "build phase" vs "under attack", "N kills · N leaked").
2. **Main stage — two columns:**
   - **Left: the board.** A header strip with a location tag and small status chips (current speed multiplier, sound on/off, currently selected tower). Below it, the game `<canvas>` (fixed internal resolution, CSS-scaled responsively, device-pixel-ratio aware). Overlaid on the canvas: a centered sweeping wave-start banner, and a full-cover "game over" overlay (hidden by default) showing a title, flavor text, four end-of-run stats (waves held / kills / score / towers), and a restart button. Below the canvas: a status strip with a one-line contextual instruction (bold key phrase + detail) and a thin horizontal "pressure" bar showing enemies-remaining-in-wave as a percentage fill.
   - **Right: a vertical rail of panels:**
     - **Wave control:** big primary "Start Wave N" button (disables and shows live remaining-enemy count while a wave is active, and reads "Run terminated" after game over); a row of two small ghost buttons for speed toggle (1×/2×) and sound mute; an auto-chain-waves toggle switch with a live "(Ns)" countdown label; a wrapping list of small pill "chips" previewing the next wave's enemy composition (icon-colored dot + count × name per enemy type).
     - **Arsenal (shop):** one card per tower type, each a horizontal card with: a colored icon swatch, tower name + a small number badge showing its hotkey, a one-line blurb, three small "pip" meters (rated 1–5 dots) for Damage/Rate/Range, and the coin cost on the right. Selected card is visually highlighted; unaffordable cards are dimmed. Clicking arms placement mode.
     - **Inspector:** context-sensitive info panel. Shows placement-mode info (name, cost, DPS, range) when a tower type is armed; shows a selected built tower's live stats (tile coordinate, damage, fire rate, computed DPS, range, splash/slow if applicable, kills credited) plus a "Sell +N" button when a tower is selected; otherwise shows a generic hint block plus running totals (towers standing, coin reserve).
     - **Field log:** a scrolling capped list (~6 items) of the most recent events, color-coded left-border by severity (info/good/warn/bad), newest on top; a small "Restart run" danger button beneath it.
3. **Field manual section (below the fold):** three cards revealed on scroll —
   - A wide numbered step list ("Field manual") teaching the core loop in ~5 steps (read the path, corners are efficient, mix tower effects, starting waves pays a bonus, selling refunds 70%).
   - A "Bestiary" card listing each enemy type with a colored icon dot, name, one-line flavor description, its coin reward (or "Boss"), and two small relative bar-meters (HP and Speed, scaled against the strongest enemy of each stat).
   - A "Controls" card: a plain key/action list (select tower 1/2/3, place = click, inspect/sell = click / S, cancel = Esc/right-click, start wave = Space, fast-forward = F, mute = M, restart = R).
4. **Footer:** small caps left label (file/build description) and a right-aligned rotating tip string that fades in/out every ~6.5s.

### 4. Grid, path & board geometry
- Internal canvas resolution: fixed tile grid, e.g. 20 columns × 12 rows of 48px tiles (960×576 canvas), rendered at devicePixelRatio and scaled responsively via CSS.
- Define the enemy path as an ordered list of grid waypoints entering off-canvas on the left and exiting off-canvas on the right, forming a zig-zag with at least 2–3 turns (e.g. enter row 2 → down → across → up → across → out). Compute actual pixel waypoints from tile centers, then build a list of line segments with cumulative arc-length so any distance-along-path can be converted to an (x, y, heading) pose — this is the single source of truth for both enemy movement and path-aligned decorative chevrons.
- Mark every grid cell the path occupies as unbuildable. Scatter a fixed set of decorative props (trees / rocks / bushes) on other off-path cells, also unbuildable, seeded deterministically so layout is stable across reloads.
- Prerender the entire static board once to an offscreen canvas (grass texture with subtle per-tile checker tint and hand-drawn blade strokes, soft random light patches, the dirt road as 3–4 stacked stroked path outlines of decreasing width/lightness for a beveled look, scattered pebble/highlight speckles along the road, a faint 1px build grid, tiny wildflower dots on open grass, hand-drawn prop sprites, a glowing spawn cave mouth on the west edge, a small crenellated stone gate/base on the east edge with a life-count banner, corner UI brackets, and an edge vignette) and blit it each frame instead of redrawing static geometry — only dynamic entities/effects are drawn per-frame on top.

### 5. Entities

**Enemies** (data-driven table: name, base HP, base speed, coin reward, score value, radius, damage-to-lives-on-leak, color, flavor line). Include at least:
- A cheap balanced baseline unit (available from wave 1).
- A fast/fragile unit (unlocks a couple waves in).
- A slow/tanky unit (unlocks mid-game, meant to be countered by splash damage).
- A rare heavy "boss" unit that appears periodically (e.g. every 5th wave), with much higher HP/reward/score and a bigger life-penalty on leak, plus a visually distinct spiky/glowing rendering and its own persistent boss health bar rendered at the top of the canvas while alive.
Each enemy sprite: soft ground shadow, bobbing walk cycle, gradient-shaded rounded body with type-specific shape treatment (round grunts with simple feet, angular tanky brutes with a wobble rotation, spiky/crowned boss with rotating spike ring and idle rotation), directional eye pair, a floating HP bar above the head that recolors green→amber→red as it depletes, a brief white damage flash, and a frost overlay effect (tinted ring + orbiting ice specks) while slowed.

**Towers** (data-driven table: name, cost, range, damage-per-shot, fire rate, projectile speed, colors, blurb, three 1–5 "pip" ratings for dmg/rate/range, plus special fields). Include at least three:
- A cheap rapid-fire single-target tower (the backbone/default).
- A support tower that deals lower damage but applies a slow (reduced speed % for a duration) on hit.
- A slower, more expensive tower that fires a lobbed shot dealing splash damage in a radius (with damage falloff by distance from impact center) — the counter to tanky enemies.
Each tower sprite: a beveled square base plate with corner rivets, a rotating turret barrel that smoothly eases toward its current target's angle, a glowing head/core, a muzzle-flash glow on fire, a brief pulse ring, and small pip dots below the base that fill in as it accumulates kill milestones.

### 6. Wave & economy system
- Player starts with a set amount of coin (e.g. 250) and lives (e.g. 20).
- Each wave is procedurally generated from the wave number: enemy counts scale up with wave number per type (later types only start appearing after a threshold wave), health scales with a formula that increases steadily with wave and accelerates slightly after a later wave, spawn types are interleaved (not grouped) so composition feels mixed, and spawn gap between enemies shrinks slightly as waves progress.
- Boss ("warlord") waves recur on a fixed cadence (e.g. every 5th wave) and their *count* escalates on a slower cadence than their appearance, so the game keeps ramping well past the point where a single extra boss stops being scary. A workable formula: `bossCount = 1 + floor(wave / 10)`, uncapped — so waves 5–9 send 1 warlord, waves 10–19 send 2, waves 20–29 send 3, waves 30–39 send 4, and so on indefinitely. Do not hard-cap this at 2; let it keep climbing every 10 waves as the wave number grows, since the escalating swarm-of-bosses moment is the intended late-game difficulty spike. Space multiple bosses in the spawn queue with their own extra delay (larger than normal spawn gap) so they don't all arrive in an instant clump, and keep scaling their individual HP with the normal wave-based health formula (optionally with a small boss-only multiplier) so more bosses doesn't mean *weaker* bosses. Update the next-wave preview chip to show the live boss count (e.g. "3× Warlord") and consider bumping the boss telegraph (banner text, spawn log line) to call out stacked-boss waves specifically.
- A "next wave preview" UI always shows composition chips for the upcoming wave before the player commits.
- Starting a wave: lock the start button, show remaining-enemy count on it, sweep the wave-number banner, log an event, play a fanfare sound.
- Clearing a wave (queue empty and no enemies alive): pay a coin bonus that scales with wave number, add score, show a floating "+N COIN" text over the board, play a clear jingle, increment the wave counter, refresh the next-wave preview, and (if auto-chain is on) start a countdown to auto-start the next wave.
- An "auto-chain waves" toggle switch with a short delay countdown, visibly displayed, so the player can walk away and let waves roll.
- A speed toggle cycling **1× → 2× → 3× → 4× → back to 1×** that runs multiple simulation steps per animation frame (i.e. call the update function N times per rendered frame for N×) rather than scaling delta time, keeping physics/collision stable at all speeds. Reflect the current multiplier in both the side-panel button and the board-header chip (e.g. "Speed 3×"), and let the F key cycle through the same sequence.
- Enemy kill reward scales slightly with wave number. Leaking an enemy at the gate subtracts its damage value from lives, triggers a red flash/shake, a floating "-N LIFE" text, a warning log line, and a "leak" sound; lives hitting zero triggers game over.

### 7. Placement & tower management
- Selecting a shop card arms "placement mode": hovering the canvas shows a ghost tower preview at the hovered tile with its range circle, tinted green/valid or red/invalid depending on affordability and cell availability (not on path, not on decor, not already occupied), with a dashed rotating-dash range ring and an X icon over invalid tiles.
- Clicking a valid tile in placement mode spends coin, instantiates the tower with a small spawn "pop-in" scale animation, spawns a placement ring effect, plays a two-tone placement sound, and logs the event.
- Clicking an existing tower outside placement mode selects it for inspection: shows a highlighted range ring and a pulsing selection ring around the tower, and lets the player sell it from the inspector panel for a partial refund (e.g. 70% of cost), which removes it, refunds coin, spawns a burst effect + floating refund text, plays a sell sound, and logs the event.
- Right-click or Escape cancels placement mode. Hovering a placed tower while nothing is armed shows a faint preview of its range ring.

### 8. Combat simulation
- Each tower on cooldown scans all live enemies within range and locks onto the one furthest along the path (closest to leaking) as its target; it eases its turret angle toward the target every frame and fires when its cooldown reaches zero.
- Projectiles are simple physics objects that home toward their target's live position each frame (falling back to the last known point if the target died mid-flight), leave a short fading trail, and resolve on arrival: single-target shots apply damage (and slow, if the tower applies one) directly to the target; splash shots apply falloff damage to every enemy within a radius of the impact point regardless of who was targeted, plus their own visual/audio impact.
- Enemy death: mark dead, pay reward coin, add score, credit the owning tower's kill counter, spawn a colored particle burst (bigger for boss kills, plus a shockwave ring and screen shake), play a kill sound and a coin chime, and refresh the shop/inspector (affordability may have changed).

### 9. Feedback & juice
- A generic particle system with two effect kinds: short-lived colored "sparks" (radial burst with gravity and drag) and expanding "ring" pulses (used for placements, splash impacts, deaths, leaks).
- Floating combat text (colored, outlined for legibility, drifting upward and fading) for coin gains, life losses, and wave-clear bonuses.
- A screen-shake value that decays exponentially each frame, triggered by leaks (scaled by damage) and boss deaths, applied as a small random camera offset during render.
- Idle ambient life independent of the game state: a handful of firefly-like glowing motes drifting and bobbing across the board with additive blending, and a few very soft moving "cloud shadow" ellipses drifting across the terrain.
- A tiny procedural audio engine built on the Web Audio API (no audio files) — short oscillator "blips" (square/triangle/sawtooth, with optional pitch ramp) and filtered noise bursts for: shooting (per tower type, rate-limited so rapid volleys don't audio-clip), impact hits, splash booms, kill chime, coin chime, tower placement, tower sell, life-leak, wave-start fanfare (ascending 4-note arpeggio), wave-clear jingle (ascending 3-note), and a descending game-over fanfare. All sounds mutable via a UI toggle.

### 10. Save / load a game
Add a persistence layer so a run can be paused and resumed later, or shared as a file:
- **Format:** a structured, human-readable save format — plain JSON with stable, self-explanatory key names (not minified, not a custom binary/base64 blob), pretty-printed with indentation so a curious player can open it in a text editor and understand or hand-edit it. Include a top-level `version` field (schema version, e.g. `1`) and a `savedAt` ISO timestamp so old saves can be migrated or rejected gracefully later.
- **What to serialize:** money, lives, current wave number, score, cumulative kills/leaked count, towers-built count, the auto-chain and sound/speed preference flags, and — most importantly — the full list of placed towers (type, grid cell, accumulated kills) so the board reconstructs exactly. Do **not** try to serialize an in-flight wave (live enemy positions, in-flight projectiles, particles) — instead, if a wave was active when saved, record that fact and resume at the *start* of that same wave number (or simply always save/restore at wave boundaries) so loading a save always drops the player into a clean build phase rather than mid-combat chaos.
- **UI:** two buttons alongside the existing Restart control — "Save game" and "Load game". Save serializes current state and triggers a file download (e.g. `bulwark-save-wave-12.json`, filename embeds the current wave for easy identification) using a Blob + temporary anchor click, no server round-trip. Load opens a hidden `<input type="file" accept=".json">`, reads the chosen file with `FileReader`, `JSON.parse`s it, validates the shape (reject / log a clear error via the field log if fields are missing, wrong types, or the version is unsupported — never throw an uncaught exception into the game loop), and if valid: resets all runtime state, replays the saved towers back onto the grid (respecting cost-free reconstruction — don't re-charge coin for towers that already exist in the save), restores the HUD counters, refreshes every panel (shop/inspector/log/wave-preview), and logs a confirmation line ("Save loaded — resuming at wave 12.").
- **Autosave (optional but recommended):** also persist the same JSON blob to `localStorage` after every wave clear and every tower placement/sale, under a fixed key (e.g. `bulwark-autosave`), and on page load offer to resume it ("Continue Wave 12?" prompt or a small banner with Resume/Discard) before falling back to a fresh game. Keep the manual file-based Save/Load as the primary, explicit mechanism — localStorage autosave is just a convenience safety net and must use the exact same schema so the two are interchangeable.
- **Integrity:** guard every load path with try/catch; a malformed or hand-edited-into-invalid-state file should degrade to a rejected load with a log message, never a blank screen or thrown error.

### 11. Match modes & wall-clock timer
The core loop above is easy to "solve" by spamming one cheap-but-strong tower (e.g. the splash tower) indefinitely with no real cost to playing forever — this both trivializes late waves and makes the game unsuitable for timed tournaments where every player needs a fair, known, finite window. Add a **match mode** selector alongside a **real wall-clock timer** to fix both problems at once:

- **Endless** (the default described above) — no clock, unchanged.
- **Timed Sprint** — a wall-clock duration (default 10:00, adjustable e.g. 1–60 minutes before the run starts) counts down in *real elapsed time*, completely independent of the 1×–4× simulation-speed multiplier — running at 4× lets a player clear more waves and score more points inside the same real minutes, but it does not buy them more real minutes. The instant the clock reaches 0:00, the run ends immediately: freeze the simulation, show a distinct "TIME'S UP" end screen (visually different from the defeat screen — e.g. a gold/amber accent instead of red — since running out of time isn't necessarily a loss), report the final score/wave/kills, and lock further interaction until restart. **The winner of a Timed Sprint round is whoever has the highest accumulated score when their own clock expires or their lives run out, whichever comes first** — this is the primary tournament mode, since every competitor gets an identical, known time budget and must be both smart (efficient builds) and fast (decisive under time pressure) to win.
- **Timed Sudden Death** — the same wall-clock setup, but instead of ending the run at 0:00, it transitions into a forced **final stand**: the arsenal locks completely (no new towers can be placed, no towers can be sold — the shop visibly dims/locks), auto-chain waves is forced on, simulation speed is forced to 4× (overriding whatever the player had chosen), and the game keeps running unattended, wave after wave, until the player's lives are fully depleted, at which point the normal defeat screen appears with the final score. This mode specifically tests whether the defense built during the timed window is actually self-sufficient, rather than dependent on the player's continued intervention — a good player must plan a build that can hold on its own, not just one that performs well with a human constantly adjusting it.

Implementation notes:
- Read the timer countdown from the same *unscaled*, real per-frame delta time already available in the render loop (before it gets multiplied by the speed-multiplier step count) — this guarantees the clock reflects actual wall-clock time no matter the chosen simulation speed.
- Let the player choose match mode and (for timed modes) the duration in minutes from the Wave Control panel before the run starts; once the first wave is launched, lock the selector (visually disable it, note that it's "locked for this run") so a match's rules can't be changed mid-round — critical for tournament fairness.
- Reflect the mode and remaining time prominently: a HUD "Clock" stat (showing "∞" for Endless) and a compact chip in the board header; give the clock stat an urgent visual treatment (e.g. recolor to the danger accent) under some threshold like 60 seconds remaining.
- During the final stand, visibly communicate the lockdown: a sweeping banner ("FINAL STAND · ARSENAL LOCKED"), a distinct log entry, dimmed/disabled shop cards, a disabled speed button pinned at 4×, and an auto-chain toggle that's visibly forced on and non-interactive.
- Match-mode configuration (mode, duration) and the live countdown belong in the save-file schema (see above) so a saved timed run resumes with an accurate remaining clock rather than a full reset — bump the save schema's version when adding these fields, and have the loader apply sensible defaults (mode = Endless) when reading an older save that predates them.

### 12. Anti-spam economy & "smartness" pressure
Beyond the timer, add mechanics that make raw tower quantity or a single dominant tower type a weaker strategy than deliberate, mixed play — a wall clock rewards efficiency, but these push toward smarter allocation even in Endless mode:

- **Escalating same-type cost ("spam tax").** Each tower's purchase price scales up with how many towers of that *same type* are already standing on the field: `cost = round(baseCost × (1 + existingCountOfThatType × 0.12))`. A first Dart Post costs base price; a second costs +12%, a third +24%, and so on. Selling a tower lowers the count and future costs for that type again. Reflect the live, current cost (not the flat base price) everywhere cost is shown or checked: the shop card, the placement ghost's affordability check, the status strip, and the inspector.
- **Mixed-arsenal bonus.** Coin and score earned per kill are multiplied by a small bonus based on how many *distinct* tower types are currently on the field: `multiplier = 1 + 0.08 × (distinctTypesOnField − 1)`, so running one type earns the base rate, two types earns +8%, all three earns +16%. Surface this in the HUD (e.g. append the live multiplier to the "per kill" sub-label once it's above 1×) so the incentive is visible, not hidden.
- Document both mechanics plainly in the field manual and the tower inspector (e.g. "cost rises 12% per existing copy of this tower") so the pressure feels like a legible rule to optimize around, not an opaque penalty.

Other directions worth considering for further difficulty/skill progression (not required, but good candidates for a future pass): an idle-coin "interest" mechanic that rewards banking unspent coin between waves over impulsively maxing out spend the instant it's available; a soft cap on total towers that pushes toward upgrading existing towers rather than tiling the map; occasional "elite" enemy variants with a resistance to one damage type and a weakness to another, forcing build adaptation rather than a single fixed optimal loadout; and a per-wave time limit that penalizes players who out-build the wave's pace rather than matching it efficiently.

### 13. Controls
Support full keyboard play alongside mouse/touch: number keys to arm each tower type, Escape to deselect/cancel, Space/Enter to start the next wave, F to toggle speed, M to toggle sound, S to sell the selected tower, R to restart the run. Mouse: click to place/select, right-click to cancel placement.

### 14. Game over & restart
On lives reaching zero: freeze simulation (stop spawning/moving/firing but keep ambient/particle animation running), show the full-canvas overlay with a red title, flavor subtext, and four final stats, disable the start-wave button, log a defeat line, play the descending fanfare. A restart button (in the overlay, in the side rail, and via the R key) fully resets all game state back to starting coin/lives/wave 1 and re-renders every panel.

### 15. Responsiveness & accessibility
Reflow the two-column stage into a single column and the topbar into a stacked layout below a breakpoint; hide less-critical sub-labels at narrow widths; respect `prefers-reduced-motion` by collapsing animation/transition durations; keep all interactive elements keyboard-reachable with visible focus states.

### 16. Implementation notes
- Single `<canvas>` element, 2D context, manual game loop via `requestAnimationFrame` with clamped delta time.
- Keep all game data in one central mutable state object (money, lives, wave, score, kill/leak counters, arrays of enemies/towers/projectiles/particles/floating-texts, current wave queue, selection state, hover cell, speed/auto/sound flags, shake/flash timers) so it can be trivially reset for restart. Structure it so the "durable" fields needed for a save (money, lives, wave, score, counters, tower list, preference flags) are cleanly separable from "transient" per-frame fields (enemies, projectiles, particles, floating texts, hover/hit-flash timers) — this makes the save/load serializer a matter of picking a subset of the state object rather than writing a parallel data model.
- Keep enemy/tower/type definitions as small config objects/tables (not hardcoded scattered literals) so balance is easy to retune.
- Use a small deterministic seeded PRNG for anything that must look random but stay stable across reloads (decor placement, background texture speckling, ambient motes).
- No external game framework — vanilla JS, inline CSS, one HTML file.
